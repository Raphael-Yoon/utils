### 📌 [Q01 (전체 26번)] 클린 아키텍처(Clean Architecture) 기반 패키지 P1(Entities), P2(Use Cases), P3(Interface Adapters), P4(Frameworks & Drivers)가 있다. P4가 P1을 직접 참조할 때 발생하는 문제와 가장 관련이 깊은 설계 지표는?

**📋 문제 본문:**


**🎯 정답:** ① 안정된 의존성 원칙(SDP) 위반과 불안정성(Instability) 지표

**💡 핵심 해설 및 실시간 Q&A 상세 대화 노트:**
정답: ①

[해설]
클린 아키텍처는 바깥쪽(프레임워크/드라이버)이 안쪽(엔티티)에 의존해야 하는 의존성 규칙을 가지며, 이는 안정된 의존성 원칙(SDP)과 관련이 깊습니다. 불안정한 계층(P4)이 안정적인 계층(P1)을 참조하는 것이 원칙에 맞으므로, 이 구조 자체를 평가하는 지표는 불안정성(Instability) 지표입니다.

💡 [실무 쟁점 & 핵심 Q&A 노트]
• 클린 아키텍처(Clean Architecture): 로버트 C. 마틴 제안. 핵심 비즈니스 로직(엔티티/유스케이스)을 UI, DB, 웹 프레임워크 등 기술적 세부사항으로부터 철저히 격리.
• 계층 의존성 규칙 (Dependency Rule): 의존성은 항상 바깥쪽(세부사항)에서 안쪽(고수준 정책)으로만 향해야 함 (P4 프레임워크 → P3 어댑터 → P2 유스케이스 → P1 엔티티).
• SDP(안정된 의존성 원칙) & 불안정성 지표: I = Ce / (Ca + Ce). 들어오고 나가는 선 중 '나가는 선(Ce)'의 비율. P1 엔티티(I=0, 최대 안정)로 의존이 흘러야 함.
• SOLID와의 관계: SOLID가 클래스 레벨의 설계 원칙이라면, 클린 아키텍처는 이를 패키지/시스템 전체로 확장한 종합 아키텍처임.

### 📌 [Q03 (전체 28번)] 소프트웨어 테스트 설계 기법 중 명세기반(블랙박스) 기법에 해당하지 않는 것은?

**📋 문제 본문:**


**🎯 정답:** ③ 조건/결정 커버리지(Condition/Decision Coverage)

**💡 핵심 해설 및 실시간 Q&A 상세 대화 노트:**
정답: ③

[해설]
동등분할, 경계값 분석, 결정 테이블은 명세(요구사항)를 기준으로 테스트 케이스를 도출하는 명세기반(블랙박스) 테스트 기법입니다. 조건/결정 커버리지는 소스코드의 내부 논리 구조를 분석해 테스트하는 구조기반(화이트박스) 테스트 기법에 해당하므로 ③번이 정답입니다.

💡 [실무 쟁점 & 핵심 Q&A 노트]
• 블랙박스(명세기반) vs 화이트박스(구조기반) 본질:
  - 블랙박스: 소스코드를 보지 않고 명세서/화면 입출력만 보고 테스트 (동등분할, 경계값 분석, 결정 테이블, 상태전이).
  - 화이트박스: 소스코드를 직접 열고 if문 조건/루프/경로를 검증 (구문, 분기, 조건/결정, MC/DC 커버리지).
• 실무 예시 (전표 10만원 전결/승인):
  - 블랙박스: 화면에서 99,999원, 100,000원, 100,001원을 입력해 결재선 생성 확인 (경계값 분석).
  - 화이트박스: ApprovalService.java의 `if (amount <= 100000)` 분기가 실제로 참/거짓으로 타는지 검증.
• MECE 관점: 복합 조건문에서 누락/중복 없는 완전 검증을 코드 레벨에서 하면 '조건/결정 커버리지', 표로 설계하면 '결정 테이블'임.

### 📌 [Q04 (전체 29번)] 다음 시퀀스 다이어그램이 나타내는 디자인 패턴으로 가장 적절한 것은? (Client가 Master에 요청 시, Master가 다수의 Slave에게 작업을 분배하고 결과를 취합하여 Client에 반환하는 구조)

**📋 문제 본문:**


**🎯 정답:** ① Master-Slave 패턴

**💡 핵심 해설 및 실시간 Q&A 상세 대화 노트:**
정답: ①

[해설]
Master가 다수의 Slave(Worker)에게 작업을 분배하고 각 Slave의 처리 결과를 취합하여 최종 결과를 반환하는 구조는 병렬/분산 처리에 흔히 사용되는 Master-Slave(Master-Worker) 패턴에 해당합니다. 따라서 정답은 ①번입니다.

💡 [실무 쟁점 & 핵심 Q&A 노트]
• Master-Slave 아키텍처 패턴: Master가 작업을 분할(`split`)하여 여러 Slave(Worker)에게 병렬 분배(`par`)하고, 결과를 취합(`merge`)하여 반환하는 분할 정복(Divide & Conquer) 패턴.
• 시험 다이어그램 객체 식별: `:Main`(Master)과 2개의 `:Controller`(Slaves)로 구성.
• Master-Slave vs Observer 결정적 차이:
  - Master-Slave: 양방향 일감 분배 및 결과 취합(`merge` 필수!).
  - Observer: 1:N 상태 변경 일방적 통지(`notify`만 있고 취합 없음).
• 하드웨어 연계: 멀티코어, 다중 CPU(SMP/NUMA), 분산 클러스터 서버 환경에서 물리적 병렬 연산(True Parallelism) 수행.

### 📌 [Q05 (전체 30번)] 다음 클래스 다이어그램에 대한 설명으로 가장 적절한 것은?

**📋 문제 본문:**


**🎯 정답:** ② Class1은 추상클래스이며, Class2와 일반화(generalization, 속이 빈 삼각형 실선) 관계로 표현된다.

**💡 핵심 해설 및 실시간 Q&A 상세 대화 노트:**
정답: ②

[해설]
1) Class1의 이름이 이탤릭체(기울임꼴)로 표기되어 있으므로 추상클래스(abstract class)입니다.
2) Class2에서 Class1으로 향하는 '실선 + 속이 빈 삼각형'은 상속(extends)을 나타내는 일반화(Generalization) 관계입니다.
3) Class2 내부의 `- attr1 : int{readOnly}`는 final 변수(읽기 전용), 밑줄 친 `- attr2 : int`는 static 정적 변수를 의미합니다.
따라서 정답은 ②번입니다.

💡 [실무 쟁점 & 핵심 Q&A 노트]
• UML 클래스 다이어그램 4대 시각 표기법:
  1) 이탤릭체(*Class1*): 추상클래스 (Abstract Class)
  2) 실선 + 속이 빈 삼각형(△): 일반화 (Generalization / 클래스 상속 extends)
  3) `- attr1: int{readOnly}`: private 접근자 및 Java `final` 읽기 전용 제약
  4) 밑줄 친 `- <u>attr2: int</u>`: Java `static` 클래스 정적 변수
• 추상클래스/인터페이스의 본질: 자식 클래스가 필수 기능을 반드시 코딩하도록 강제하는 '구현의 계약(Contract)' 역할.

### 📌 [Q06 (전체 31번)] ISO/IEC 25023에서 정의하는 신뢰성(Reliability) 측정 항목으로 가장 적절하지 않은 것은?

[해설]
ISO/IEC 25023에서 신뢰성 관련 측정 항목은 MTBF, MTTR, 가용성 등 시스템의 고장·복구·가동 관련 지표들로 구성됩니다. '결함 발견율'은 테스트 프로세스의 효과성을 나타내는 지표로 신뢰성 측정 항목이 아니므로 ③번이 정답입니다.

### 📌 [Q07 (전체 32번)] SysML Requirement Diagram에서 요구사항 간의 관계로 옳은 것을 모두 고른 것은?

**📋 문제 본문:**


**🎯 정답:** ① 가, 나, 다

**💡 핵심 해설 및 실시간 Q&A 상세 대화 노트:**
정답: ①

[해설]
SysML Requirement Diagram의 요구사항 간 관계에는 derive(파생), satisfy(만족), verify(검증), refine(정제), trace(추적), copy(복사) 등이 있습니다. 'include'는 UML 유스케이스 다이어그램에서 사용하는 관계이며 SysML 요구사항 관계가 아니므로, 옳은 것은 가·나·다이고 정답은 ①번입니다.

💡 [실무 쟁점 & 핵심 Q&A 노트]
• SysML(Systems Modeling Language): UML 2.0에 하드웨어, 인력, 수학/물리 수식, 요구사항 추적을 결합한 시스템 공학 전용 확장 언어.
• 4대 영역 및 9대 다이어그램: 요구사항(Req), 구조(BDD, IBD, Pkg), 동작(Act, Seq, Stm, Uc), 파라메트릭(Parametric).
• 요구사항 다이어그램 3대 핵심 관계:
  - `<<derive>>`: 상위 요구사항에서 하위 요구사항 도출
  - `<<satisfy>>`: 설계 부품(블록)이 요구사항을 충족함
  - `<<verify>>`: 테스트 케이스가 요구사항 충족을 시험/검증함.

### 📌 [Q08 (전체 33번)] AI 모델의 추론 결과에 대해 입력 데이터의 범위 및 기대 결과 조건을 지정하고, 그 범위 내 모든 입력 데이터가 조건을 만족하는지 확인하는 AI 테스트 기법으로 가장 적절한 것은?

**📋 문제 본문:**


**🎯 정답:** ② 커버리지 테스트(coverage testing)

**💡 핵심 해설 및 실시간 Q&A 상세 대화 노트:**
정답: ②

[해설]
커버리지 테스트 기법(coverage testing)은 입력 데이터의 범위 및 기대하는 추론 결과의 조건을 지정하고, 그 범위 내 모든 입력 데이터에 대해 학습 완료 모델의 추론 결과가 해당 조건을 만족하는지 확인하는 기법입니다. 참고로 메타모픽 테스트는 입력 변화에 따른 추론 결과의 관련성을 이용하고, 뉴런 커버리지 테스트는 뉴런의 활성화 정도를 측정하며, 적대적 공격 기법은 인위적 노이즈로 오작동을 유도하는 기법입니다. 따라서 정답은 ②번입니다.

💡 [실무 쟁점 & 핵심 Q&A 노트]
• AI 테스팅 4대 기법 실무 비교:
  1) 커버리지 테스트: 지정된 입력 범위 내 모든 데이터가 안전/기대 조건을 만족하는지 검증 (예: 제동거리 0.1~5m 내 감속도 80% 보장).
  2) 메타모픽 테스트: 정답 라벨이 없을 때(No Oracle), 1개 데이터를 회전/변형해도 결과 관계가 유지되는지 검증.
  3) 뉴런 커버리지 테스트: 딥러닝 내부 뉴런 활성화 비율을 자동화 도구가 측정하는 AI 화이트박스 메트릭.
  4) 적대적 공격: 사람 눈에 안 보이는 미세 노이즈를 섞어 AI 오분류를 유도하는 강건성 시험.

### 📌 [Q14 (전체 39번)] 다음 의사 코드(Pseudo Code)에 대하여 McCabe의 Complexity Number를 계산한 것으로 가장 적절한 것은? (단, 코드 실행에 대한 오류는 없는 것으로 가정함)

**📋 문제 본문:**


**🎯 정답:** ② 4

**💡 핵심 해설 및 실시간 Q&A 상세 대화 노트:**
정답: ②

[해설]
순환복잡도(Cyclomatic Complexity)는 CC = P + 1 (P는 분기 노드 수) 공식으로 계산합니다. 코드의 분기 노드는 if 2개, for 1개로 총 3개이므로, CC = 3 + 1 = 4가 되어 정답은 ②번입니다.

💡 [실무 쟁점 & 핵심 Q&A 노트]
• McCabe 순환 복잡도: V(G) = P + 1 (P = 참/거짓을 판단하는 조건 분기문의 개수).
• 조건 세기 원칙:
  - `if (조건)`: +1
  - `else if (조건)`: +1 (새로운 조건 검사이므로 추가)
  - `else`: +0 (새 조건이 아닌 기본 False 출구이므로 카운트 X, +1 기본길에 포함)
  - `for (조건)`: +1 (탈출 판단 조건이 있으므로 카운트)
  - `if (A && B)`: +2 (단락 평가로 조건이 2개이므로 각각 카운트)
  - 순수 무한루프 `while(true)`: +0 (탈출 판단 조건이 없으므로 카운트 X).
• 본질: 프로그램을 100% 테스트하기 위해 필요한 '최소 독립 기저 경로(Basis Paths)'의 수.

Staff가 Service 인터페이스를 implements하는 관계는 실체화(Realization, 점선+속이 빈 삼각형)로, Person 클래스를 extends하는 관계는 일반화(Generalization, 실선+속이 빈 삼각형)로 표현합니다. 또한 doWork() 메서드 내에서 Task 객체를 지역적으로 생성해 사용하는 것은 의존/연관 관계로 실선 화살표를 사용합니다. 이 세 관계를 모두 올바르게 표현한 것은 ④번입니다.

💡 [실무 쟁점 & 핵심 Q&A 노트]
• UML 클래스 다이어그램 4대 관계선 총정리:
  1) `extends Person` (상속/일반화): 실선 + 속이 빈 삼각형(△)
  2) `implements Service` (구현/실체화): 점선 + 속이 빈 삼각형(△)
  3) `private Task task` (멤버변수/연관): 실선 화살표(→)
  4) `Task t = new Task()` (로컬변수/의존): 점선 화살표(⇢)
• 암기 팁: 상속/구현은 무조건 '속이 빈 삼각형', 객체 참조/사용은 무조건 '단순 화살표'!

### 📌 [Q20 (전체 45번)] 보통의 경우 Normal 유스케이스 시나리오가 사용되지만 특정 조건 하에서 Conditional 유스케이스 시나리오가 사용된다는 UML 표기법으로 가장 적절한 것은?

**📋 문제 본문:**


**🎯 정답:** ④ Normal ⇠«extend»⇠ Conditional

**💡 핵심 해설 및 실시간 Q&A 상세 대화 노트:**
정답: ④

[해설]
특정 조건 하에서 선택적으로 실행되는 유스케이스는 확장관계(extend)로 표현하며, '확장 기능 유스케이스'(Conditional)에서 '확장 대상 유스케이스'(Normal) 방향으로 점선 화살표를 연결하고 <<extend>>라고 표기합니다. 따라서 Conditional에서 Normal로 향하는 extend 관계인 ④번이 정답입니다.

💡 [실무 쟁점 & 핵심 Q&A 노트]
• UML 유스케이스 관계 1초 판별법:
  - `<<include>>`: 100% 필수 실행 (화살표: 기본 ➔ 필수포함)
  - `<<extend>>`: 특정 조건 하 선택적 실행 (화살표: 부가/확장 ➔ 기본기능)
• 결제/주문/쿠폰 다이어그램:
  `[주문하기]` ──«include»──► `[결제하기]` ◄──«extend»── `[쿠폰할인]`
  (include와 extend가 결제하기를 중심으로 화살표 머리를 마주 봄).

### 📌 [Q22 (전체 47번)] RESTful 서비스의 사용 예로 가장 적절하게 묶은 것은?

**📋 문제 본문:**


**🎯 정답:** ③ 나, 라

**💡 핵심 해설 및 실시간 Q&A 상세 대화 노트:**
정답: ③

[해설]
HTTP 표준 메서드는 GET, POST, PUT, DELETE, PATCH 등이며 'READ'와 'UPDATE'는 존재하지 않는 메서드명입니다. 가(READ)와 다(UPDATE)는 잘못된 메서드를 사용하고 있어 부적절하며, 나(POST로 생성)와 라(DELETE로 삭제)는 올바른 RESTful 사용 예이므로 정답은 ③번(나, 라)입니다.

💡 [실무 쟁점 & 핵심 Q&A 노트]
• RESTful API 4대 CRUD 표준 HTTP 메서드:
  - 조회(Read): `GET` (READ라는 메서드는 없음!)
  - 생성(Create): `POST`
  - 수정(Update): `PUT` (전체 수정) 또는 `PATCH` (부분 수정) (UPDATE라는 메서드는 없음!)
  - 삭제(Delete): `DELETE`
• URL 명사 규칙: 행위는 HTTP 메서드로 표현하고, URL에는 자원 명사(`/users/1`)만 작성.
